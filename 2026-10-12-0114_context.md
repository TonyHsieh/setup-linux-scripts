## 🛠️ 2. Detailed Answers & Technical Guidance on Your Questions

### Q1: The `https://` (bentopdf and traefik) keeps giving an "unsafe" error in the browser — can't we create a non-expiring self-signed cert for this?

#### Why the browser gives this warning:
1. **WSL2 vs. Windows Trust Stores**: `mkcert -install` registered the local Root CA (`rootCA.pem`) inside the **WSL2 Linux** certificate trust store. When you use `curl` inside Linux, it recognizes the certificate. However, when you open Chrome or Edge on **Windows**, Windows has its own separate Certificate Trust Store. Windows does not yet know about the root CA generated inside WSL2, so it flags the connection as untrusted.
2. **Why raw self-signed certs are worse**: Modern browsers (Chrome 117+, Edge, Safari) actively reject raw self-signed certificates with hard errors (`NET::ERR_CERT_AUTHORITY_INVALID`) and HSTS restrictions, forcing you to click through red warning screens or type `thisisunsafe` every session.
3. **Browser validity limits**: Chrome strictly rejects any SSL certificate that has a validity period longer than **825 days (~2.2 years)** for security reasons. Modern browsers do not allow truly "non-expiring" certificates. `mkcert` generates certificates valid for 2 years and 3 months, which is the maximum permissible lifetime.

#### The Permanent Fix (Trust the Root CA in Windows):
You only need to import the `mkcert` Root CA certificate into Windows **once**. After doing this, **all** `*.localhost` domains will show a clean, green trusted padlock in Windows browsers without any warnings.

**Option A — Via Windows PowerShell (Easiest)**:
1. Open PowerShell on Windows (press `Win + X` → Terminal / PowerShell).
2. Run this single command:
   ```powershell
   Import-Certificate -FilePath "\\wsl.localhost\Ubuntu\home\tonyh\.local\share\mkcert\rootCA.pem" -CertStoreLocation Cert:\CurrentUser\Root
   ```
   *(If your WSL distribution is named differently in Windows Explorer, replace `Ubuntu` with your distro name).*

**Option B — Via Windows Explorer GUI**:
1. In WSL2, open the folder in Windows Explorer:
   ```bash
   explorer.exe "$(wslpath -w /home/tonyh/.local/share/mkcert)"
   ```
2. Double-click `rootCA.pem` (or right-click → **Install Certificate**).
3. Select **Current User** → click Next.
4. Choose **Place all certificates in the following store** → click **Browse**.
5. Select **Trusted Root Certification Authorities** → click OK → Next → Finish.
6. Restart your Windows browser and navigate to `https://pdf.localhost`.

### Q2: How can I test if PostgreSQL is working — what do I use to log into it?

PostgreSQL is running and verified on port `5432`. Here are the easiest ways to test and log into it:

#### Option A: Direct Interactive CLI (Zero installation needed)
Run this command from your terminal to drop directly into the `psql` interactive shell inside the container:
```bash
podman exec -it local-postgres psql -U devuser -d devdb
```
Inside the `psql` prompt:
* `\l` — List all databases
* `\dt` — List all tables
* `SELECT version();` — Check database version
* `\q` — Exit `psql`

#### Option B: Quick One-Line Health Check
Run this from your terminal to verify connectivity without entering an interactive shell:
```bash
podman exec local-postgres psql -U devuser -d devdb -c "SELECT 'PostgreSQL is working!' AS status, NOW() AS timestamp;"
```

### Q3: How do I check if Puppeteer is working — the URL gives me an error page / bad gateway?

#### Why `http://puppeteer.mcp.localhost` returns `502 Bad Gateway`:
1. **Stdio vs. HTTP Server**: The official container `docker.io/mcp/puppeteer:latest` (from Anthropic's Model Context Protocol project) is an **MCP stdio server**, **not** a web server!
2. Its entrypoint is `node dist/index.js`, which reads JSON-RPC requests from standard input (`stdin`) and writes responses to standard output (`stdout`).
3. It does **not** open port 3000 or listen for HTTP connections.
4. Traefik was configured to route HTTP requests for `puppeteer.mcp.localhost` to port 3000. Because nothing is listening on port 3000, Traefik reports `502 Bad Gateway`.

#### How to test that Puppeteer MCP is actually operational:
You can verify that the containerized Puppeteer MCP engine is working right now by sending a JSON-RPC initialization handshake over `stdin`:
```bash
echo '{"jsonrpc": "2.0", "id": 1, "method": "initialize", "params": {"protocolVersion": "2024-11-05", "capabilities": {}, "clientInfo": {"name": "test", "version": "1.0"}}}' | podman run --rm -i docker.io/mcp/puppeteer:latest
```
**Expected Response**:
```json
{"result":{"protocolVersion":"2024-11-05","capabilities":{"resources":{},"tools":{}},"serverInfo":{"name":"example-servers/puppeteer","version":"0.1.0"}},"jsonrpc":"2.0","id":1}
```

#### How AI Agents (OpenCode, Hermes, Claude) actually use Puppeteer MCP:
Agents run MCP tools via standard I/O commands rather than HTTP. In OpenCode (`~/.config/opencode/opencode.json`):
```json
{
  "mcp": {
    "puppeteer": {
      "type": "local",
      "command": ["podman", "run", "-i", "--rm", "--init", "docker.io/mcp/puppeteer:latest"]
    }
  }
}
```
*Benefits*: The browser container runs on-demand only when your AI agent needs to scrape or inspect a page, without keeping an idle browser container burning memory in the background.

#### Options for Tomorrow:
* **Option 1 (Recommended)**: Remove `mcp-puppeteer` from `docker-compose.yml` so it runs on-demand via the agent's stdio config.
* **Option 2 (HTTP/SSE Adapter)**: Wrap `mcp-puppeteer` with an SSE bridge (e.g. `supergateway`) if you specifically require a persistent HTTP endpoint.
